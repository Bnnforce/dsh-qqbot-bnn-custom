# 架构说明：一条消息是怎么走完的

> 看懂这份，就知道「我改的那个文件，什么时候会被调到、能拿到什么」。
> 依据 `@zaofan/dsh-qqbot@1.13.20` 的真实实现（`dist/gateway/middleware-setup.js` 等）。

## 二、三个关键位置（改东西前先确认自己在哪一层）

| 层 | 什么时候跑 | 频率 | 能干什么 | 不能干什么 |
|---|---|---|---|---|
| **inbound 早挂点** `onInbound` | 每条入站消息，**记群历史之前** | 每条消息 | 消灭 / 改写 / 强制唤醒 | 读 `ctx.state.mention`（还没算出来） |
| **inbound 晚挂点** `onDecide` | 每条入站消息，**@门控之后** | 每条消息 | 读/改写 @ 判定、整条拦掉 | 消灭（群历史已记过） |
| **outbound** `onOutbound` | 每段**出站正文**，发送前 | 每段回复 | 改写正文、消灭、额外发消息 | 改 `msg_id`、改已发出去的内容 |

> ⚠️ **热路径纪律**：inbound 两个挂点**每条消息都跑一遍**。别在这里
> 发消息、打外部接口、做长任务。这个包曾因「每消息同步写盘 + 反射遍历 ctx」被拖慢。

## 三、六个扩展点分别在哪一层

| 目录 | 触发时机 | 谁调它 | 拿到 |
|---|---|---|---|
| `inbound/` | 每条**入站**消息 | 插件中间件链 | `ctx`（含 `message` / `platform` / `rewrite` / `annihilate`） |
| `outbound/` | 每段**出站**正文 | 发送前 | `ctx`（含 `text` / `kind` / `rewrite` / `target`） |
| `hooks/` | 插件**启动时一次** | 启动流程 | `env`（含 `caps`） |
| `commands/` | 用户敲 `/xxx` | 命令分发 | `ctx`（能力平铺） |
| `tools/` | AI 主动调用 | 工具注册表 | `(args, env, exec)` |
| `botplay/` | 卡片按钮被点 | 回调派发 | `ctx`（含 `event` / `user` / `store`） |

`botplay/` 是唯一**不从扩展包加载**的（见 README「关于 botplay」）。

## 四、数据从哪来、到哪去

```
{WORKSPACE_ROOT}/Bot/            ← 工作区（素材、人格、曲库）
{dataRoot}/                      ← qqbot 数据根（= {WORKSPACE_ROOT}/Bot/dshqqbot）
├── .qqbot/                      ← 插件自己的数据（官方维护，本包只读）
└── .qqbot-extensions/
    ├── data/                    ← 本包的共享状态（roam / wake-lottery / 缓存…）
    ├── botplay/                 ← 卡片运行时副本（本包启动时自动同步）
    └── lib/                     ← 运行时依赖副本（同上）
```

**路径唯一出口**：`lib/pack-paths.mjs`（根）+ `lib/dirs.mjs`（各数据目录）。
新代码**不要自己拼路径**，从 `dirs.mjs` 拿。

推导规则（`pack-paths.mjs`）：

```js
EXT_ROOT        = 本包所在目录（从 import.meta.url 推）
IS_PACK         = EXT_ROOT 的父目录名 === 'extension-packs'
DEFAULT_DATA_ROOT = IS_PACK ? EXT_ROOT/../.. : EXT_ROOT/..
DATA_ROOT       = env.QQBOT_DATA_ROOT    || DEFAULT_DATA_ROOT
WORKSPACE_ROOT  = env.BNN_WORKSPACE_ROOT || DATA_ROOT/../..
```

## 五、两条容易踩的「链路真相」

### ① `wakeTo` 不等于「AI 一定会说话」

`caps.wakeTo(scope, peerId, text)` 只是「往那个会话排一条消息、请求开一个回合」。
返回 `true` 只代表**已排进队列**，不代表 AI 真的回话、更不代表 QQ 送达。

它还会因为**会话被回收**而返回 `false`（插件内部 `injectToPeer` 查不到记录）。
所以调用方必须有失败路径。

### ② hook 里**没有** `sender`

`hooks/` 拿到的是 `env`（含 `caps`），但 `caps` 里**没有 `sender` / `replyTarget`**。

⇒ `caps.text()` / `caps.markdown()` 在 hook 里**恒返回 false**（不是 bug，是契约）。
hook 想主动说话，唯一正规通道是 `caps.wakeTo` —— 让 AI 说，而不是自己发。

需要自己发消息的，把发送下沉到 `tools/` 或 `commands/`（那两层有 `sender`）。

## 六、顺序敏感的三处

| 位置 | 规则 | 为什么 |
|---|---|---|
| `outbound/` | **按文件名升序**执行 | `05-birthday` → `10-ensure-at-back` → `20-dedupe` → … → `60-split-bubbles`，靠编号表达先后 |
| inbound 早/晚挂点 | 引擎固定顺序，不可调 | 早挂点在记群历史前，晚挂点在 @门控后 |
| `botplay/` 卡片 | 无顺序，按事件 `file` 字段点名加载 | — |

改 `outbound/` 的文件名等于改执行顺序，**慎改编号**。
